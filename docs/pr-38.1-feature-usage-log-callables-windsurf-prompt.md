# PR 38.1 — Route featureUsageLog through callables (RNFB auth-mismatch fix) (Windsurf prompt)

## Why this PR exists

PR 38 shipped with both writes (from `src/services/analytics.ts`)
and reads (from `src/screens/admin/AdminUsageScreen.tsx`) hitting
Firestore via the **Web SDK** (`firebase/firestore`). On native,
that SDK has its own auth context — separate from
`@react-native-firebase/auth`. So `request.auth` is `null` from
the Web SDK's perspective whenever a write or read fires from
the phone, even though the user is signed in via RNFB.

**Result:**

- **Writes:** every `addDoc(featureUsageLog, ...)` is rejected by
  the rule that requires `request.auth != null`. The catch
  block in `writeFeatureUsageLog` swallows the error to
  `console.warn`. No docs in `featureUsageLog/`. Silent failure.
- **Reads:** `getDocs(query(featureUsageLog, ...))` for the
  admin dashboard fails with the visible
  `Missing or insufficient permissions` error on tapping the
  📊 Feature Usage tile.

**This is the exact same root cause as PR 6.1's signed-PUT
fix for Storage uploads.** Same SDK-auth-context mismatch, just
on a different Firebase product (Firestore instead of Storage).
The pattern fix is also analogous: route the operation through
a Cloud Function callable, since callables pass the auth token
through the HTTPS header and work correctly regardless of which
client SDK initiated the auth.

**What ships:**

- Two new callables:
  - `logFeatureUsageEvent` — server-side write of one event doc
  - `queryFeatureUsageLog` — server-side read of events within
    a date range, admin-gated
- Client changes:
  - `analytics.ts` `writeFeatureUsageLog` replaces `addDoc` with
    the new callable, using the same web/native dispatch pattern
    as `orderService.ts`
  - `AdminUsageScreen.tsx` replaces `getDocs` with the new
    callable
- Rules tighten: `featureUsageLog/{eventId}` becomes
  server-mediated only (`allow read, write: if false`), same
  posture as `aiAuditLog/` and `auditLog/`.
- Rules tests updated to match the new posture (the existing
  16 tests need a small flip from "client CAN create with own
  uid" to "no client can create directly, server-only").

~1.5–2 hours Windsurf work. Server-first deploy. OTA-eligible
(no native changes; no new deps).

## Scope (in)

### Part 1 — Callable `logFeatureUsageEvent`

In `functions/src/index.ts`, near the existing PR 32 +
PR 34 + PR 38 territory:

```ts
// PR 38.1 — server-mediated write to featureUsageLog. Replaces
// the direct client write that PR 38 originally shipped with,
// which silently failed on native (Web SDK Firestore can't see
// RNFB auth — same root cause as the PR 6.1 signed-upload fix).
//
// Auth gate: any authenticated caller. Anonymous skipped at the
// client (writeFeatureUsageLog short-circuits when uid is null);
// defense-in-depth check here just in case.
//
// Validation is minimal because the client wrapper controls the
// shape and the data is observability-only. We DO normalize the
// feature name to a string and reject the call if it's missing,
// to keep the collection from filling with garbage.
export const logFeatureUsageEvent = onCall<{
  feature: string;
  shopId?: string;
}>(
  { cors: true, enforceAppCheck: false },
  async request => {
    const auth = request.auth;
    if (!auth) {
      // Silent — anonymous events don't write. Matches the
      // client-side short-circuit. Returning ok:false instead
      // of throwing keeps the fire-and-forget caller quiet.
      return { ok: false, reason: 'unauthenticated' };
    }

    const { feature, shopId } = request.data ?? ({} as any);
    if (typeof feature !== 'string' || !feature) {
      return { ok: false, reason: 'invalid-feature' };
    }

    // Resolve role from custom claims. Mirrors the priority
    // order in the client's currentRole() helper.
    let role: 'admin' | 'shop_owner' | 'delivery' | 'customer' = 'customer';
    if (auth.token?.admin === true) role = 'admin';
    else if (auth.token?.shopOwner === true) role = 'shop_owner';
    else if (auth.token?.delivery === true) role = 'delivery';

    const date = new Date().toISOString().slice(0, 10);
    const doc: Record<string, unknown> = {
      uid: auth.uid,
      role,
      feature,
      date,
      timestamp: FieldValue.serverTimestamp(),
    };
    if (typeof shopId === 'string' && shopId) {
      doc.shopId = shopId;
    }

    await db.collection('featureUsageLog').add(doc);
    return { ok: true };
  },
);
```

### Part 2 — Callable `queryFeatureUsageLog`

```ts
// PR 38.1 — server-mediated read of featureUsageLog for the
// admin dashboard. Replaces the direct client query.
//
// Auth gate: admin claim required. Mirror of getShopKycReadUrls'
// admin-only posture (PR 31).
export const queryFeatureUsageLog = onCall<{
  period: '7d' | '30d';
}>(
  { cors: true, enforceAppCheck: false },
  async request => {
    const auth = request.auth;
    if (!auth) throw new HttpsError('unauthenticated', 'Sign in required');
    if (auth.token?.admin !== true) {
      throw new HttpsError('permission-denied', 'Admin role required');
    }

    const { period } = request.data ?? ({} as any);
    if (period !== '7d' && period !== '30d') {
      throw new HttpsError(
        'invalid-argument',
        "period must be '7d' or '30d'",
      );
    }

    const days = period === '7d' ? 7 : 30;
    const startDate = new Date(Date.now() - days * 86_400_000)
      .toISOString()
      .slice(0, 10);

    // Same query AdminUsageScreen previously ran client-side.
    // Limit 10_000 is the same cap PR 38 had; if pilot scale
    // exceeds it, the follow-up is server-side daily-rollup
    // aggregation (already documented in PR 38's follow-ups).
    const snap = await db
      .collection('featureUsageLog')
      .where('date', '>=', startDate)
      .orderBy('date', 'desc')
      .limit(10_000)
      .get();

    const events = snap.docs.map(d => {
      const data = d.data();
      return {
        ...data,
        timestamp: data.timestamp?.toMillis?.() ?? data.timestamp ?? null,
      };
    });

    return {
      ok: true,
      events,
      truncated: snap.size === 10_000,
    };
  },
);
```

### Part 3 — Tighten `firestore.rules`

Replace the existing `featureUsageLog/{eventId}` block with:

```
// PR 38.1 — server-mediated only. The Web SDK Firestore client
// on native cannot see RNFB auth, so direct client writes/reads
// silently fail (writes) or fail with permission-denied (reads).
// Both ops now go through `logFeatureUsageEvent` /
// `queryFeatureUsageLog` callables, which use the Admin SDK
// (bypasses rules) and validate auth via the callable's
// `request.auth` (which works correctly via the HTTPS auth
// header regardless of which client SDK initialized auth).
//
// Direct read/write from clients is denied — defense-in-depth
// against forged events from a debug client.
match /featureUsageLog/{eventId} {
  allow read, write: if false;
}
```

Same posture as `aiAuditLog/` and `auditLog/`.

### Part 4 — Update `tests/rules/featureUsageLog.test.ts`

The existing 16 tests need a small posture flip. Before PR 38.1:

- "non-admin user CAN create with own uid" → expected `allow`
- "admin user CAN read" → expected `allow`

After PR 38.1, ALL direct client operations should be denied
regardless of auth state. Tests to keep or restructure:

- Anonymous user CANNOT create → `deny` (already passes)
- Authenticated user CANNOT create (any uid) → `deny` (was
  `allow`; flip)
- Authenticated user CANNOT create with forged uid → `deny`
  (already passes; reasoning changes from "uid mismatch" to
  "everyone is denied")
- Authenticated user CANNOT update → `deny` (already passes)
- Authenticated user CANNOT delete → `deny` (already passes)
- Non-admin authenticated user CANNOT read → `deny` (already passes)
- **Admin user CANNOT read directly either** → `deny` (was
  `allow`; flip — admin reads now go through `queryFeatureUsageLog`)
- Server-side write via Admin SDK is implicit and not tested
  at the rules layer.

Net: probably 10–12 tests instead of 16. Keep the test file
since rules-tests-for-this-collection is a useful pattern.

### Part 5 — Client wrappers in `orderService.ts`

Same web/native dispatch pattern as every other wrapper in
this file:

```ts
async logFeatureUsageEvent(args: {
  feature: string;
  shopId?: string;
}): Promise<void> {
  // Fire-and-forget on the caller side; the callable itself
  // returns quickly. Errors are swallowed here so analytics
  // writes never block UX. The callable returns
  // { ok: false } silently for unauthenticated / invalid
  // input; we ignore that response.
  if (isNative) {
    const fn = getNativeFunctions().httpsCallable('logFeatureUsageEvent');
    await fn(args);
  } else {
    const fn = httpsCallable(functions, 'logFeatureUsageEvent');
    await fn(args);
  }
},

async queryFeatureUsageLog(args: { period: '7d' | '30d' }): Promise<{
  ok: true;
  events: Array<{
    uid: string;
    role: string;
    feature: string;
    date: string;
    timestamp: number | null;
    shopId?: string;
  }>;
  truncated: boolean;
}> {
  if (isNative) {
    const fn = getNativeFunctions().httpsCallable('queryFeatureUsageLog');
    const result = await fn(args);
    return result.data as any;
  }
  const fn = httpsCallable(functions, 'queryFeatureUsageLog');
  const result = await fn(args);
  return result.data as any;
},
```

### Part 6 — Modify `analytics.ts` `writeFeatureUsageLog`

```ts
import { orderService } from './orderService';

async function writeFeatureUsageLog(
  name: string,
  params: EventParams,
): Promise<void> {
  try {
    const s = useAuthStore.getState();
    const uid = s.uid;
    if (!uid) return;

    const shopId = typeof params.shop_id === 'string' ? params.shop_id : undefined;

    // PR 38.1 — route through callable. The Web SDK Firestore's
    // direct addDoc was failing silently on native because the
    // Web SDK can't see RNFB auth (same root cause as PR 6.1's
    // signed-upload fix for Storage). The callable passes the
    // auth token through HTTPS so it works on both SDKs.
    await orderService.logFeatureUsageEvent({
      feature: name,
      shopId,
    });
  } catch (e) {
    // Silent — observability writes never block UX.
    // eslint-disable-next-line no-console
    console.warn('[analytics] featureUsageLog write failed:', e);
  }
}
```

The `addDoc` + `collection` + `serverTimestamp` + `db` imports
are no longer used here; remove them. The `useAuthStore` import
stays (we still need uid for the short-circuit). The
`currentRole()` helper is now unused — remove it (server resolves
the role from the auth claim).

```markdown
## Web SDK Firestore + RNFB auth — the silent-failure trap

**Hard-learned during PR 38.1 (the second hit of the PR 6.1
problem).** Any direct Firestore read or write from client code
that requires auth (read or write rules including
`request.auth != null` / role checks / uid match) will silently
fail or hard-fail on native, because the Web SDK Firestore
(`firebase/firestore`) does not share auth context with
`@react-native-firebase/auth`.

**Symptoms:**
- Writes: no docs in the target collection, console.warn lines
  only visible in dev menu, no Sentry events.
- Reads: visible "Missing or insufficient permissions" error in
  the UI.

**Fix:** route both reads and writes through Cloud Function
callables, which pass the auth token via the HTTPS header and
work cross-SDK. Mirror the orderService.ts dispatch pattern.

**When writing a Windsurf prompt:** any time the prompt
proposes direct Firestore operations from the client AND those
operations require auth, the deploy plan must specify the
callable-routed approach. Direct client → Firestore writes
should be reserved for unauthenticated or rules-open
collections (none exist in this project today).

**Affected features so far:**
- Storage uploads (PR 6 → fixed by PR 6.1 signed PUT URLs)
- Firestore writes to featureUsageLog (PR 38 → fixed by PR 38.1
  callable routing)
- Likely any future write-from-client to authenticated
  collections; prevent at prompt-writing time.
```

## Scope (out)

- **Adding `@react-native-firebase/firestore` as a native dep**
  — would allow direct Firestore writes from native, but adds
  a native config change → requires `eas build` (per the
  OTA-vs-build rule). The callable approach is OTA-eligible
  and matches existing project patterns; stay with it.
- **Batching events client-side to reduce per-event callable
  cost** — at pilot scale, callable cost is ~$0.01/month.
  Batching adds complexity for no real saving. Revisit if
  scale ever justifies it.
- **Server-side daily rollups for aggregation** — already
  documented as a future PR in PR 38's follow-ups.
  PR 38.1 stays at the client-side aggregation pattern PR 38
  established; only the data fetch changes.

## Why this PR matters

Without PR 38.1, **PR 38 doesn't actually work on native.**
- The admin dashboard hard-fails with a visible permission error.
- The featureUsageLog collection never accumulates data, so the
  pilot would launch with no Strategic Principle 7 metrics
  available even though we *thought* the substrate was in place.

The fix is small but **mission-critical for the pilot.**
PR 38's whole purpose was to be the read side of Strategic
Principle 8 (instrument before you ship). If it's silently
broken, every PR 32 + PR 34 event we've been carefully
logging since May 22 has been going nowhere.

PR 38.1 also establishes the **second instance of the same
pattern** — direct Firestore from RN client doesn't work on
native, route through callable. This pattern now applies to
two Firebase products (Storage via PR 6.1, Firestore via
PR 38.1). The discipline-doc update closes the loop so the
*third* instance never gets shipped.
