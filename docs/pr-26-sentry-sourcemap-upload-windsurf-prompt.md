# PR 26 — Sentry source-map upload via EAS secret (Windsurf prompt)

## Why this PR exists

Sentry is wired up (`@sentry/react-native ~7.2.0` in deps,
`src/services/sentry.ts` initializes with the DSN from
`app.json.expo.extra.sentry.dsn`, `app.json.plugins` includes
`"@sentry/react-native"`). Production errors arrive in the Sentry
dashboard. **But every stack trace looks like this:**

```
Error: Cannot read property 'menuItemId' of undefined
  at <anonymous>:1:24561
  at <anonymous>:1:24830
  at <anonymous>:1:25104
```

Minified single-line JS. Useless for debugging. The source maps that
would de-minify these traces are generated by Metro at build time
but are **never uploaded to Sentry** because:

1. `eas.json` sets `SENTRY_DISABLE_AUTO_UPLOAD: "true"` on **all
   three** profiles (development, preview, production) — deliberate
   to avoid uploads on non-prod builds, but no override for prod.
2. There's no `SENTRY_AUTH_TOKEN` configured as an EAS secret, so
   the upload couldn't authenticate even if it tried.
3. The `@sentry/react-native` config plugin in `app.json` has no
   `organization` / `project` field, so the plugin doesn't know
   where to upload to.

**PR 26 turns this on for production builds only.** Source maps for
preview/dev stay disabled (waste of upload bandwidth + Sentry quota
on builds that get thrown away). Once shipped, every production
crash that lands in Sentry will resolve to a real file path + line
number + symbolicated function name — the difference between "I
think the bug is somewhere in checkout" and "line 327 of
`CheckoutScreen.tsx`, `placeOrder`, the `result.razorpayOrderId`
read is the throw."

~30–45 minutes of Windsurf work + one round-trip to Sudhir to
generate the Sentry auth token and create the EAS secret.

## Critical lessons from PRs 12–25 (do not repeat)

1. **Secrets never go in app.json or app.config.js.** They go in EAS
   secrets, read at build time via `process.env`. Sudhir generates
   the Sentry org-level auth token and runs `eas secret:create` —
   Windsurf must NOT inline it into any committed file.
2. **The Sentry plugin's `organization` and `project` ARE public,
   not secret.** The org slug and project slug appear in the Sentry
   dashboard URL; they're fine to commit. Only `SENTRY_AUTH_TOKEN`
   is the secret.
3. **Server-first deploy doesn't apply** — PR 26 is a build-time
   configuration change only. No new Cloud Function. The first
   "production" build that picks up these changes will upload its
   source maps; existing OTAs do not. PR 26 effectively ships on
   the **next native build**, not on the next OTA.
4. **Never strip imports between edits in the same PR.**
   `src/services/sentry.ts` is read-only this PR. No other source
   files change.
5. **All `useState` calls in screens sit ABOVE conditional early
   returns.** N/A — PR 26 changes no screens.
6. **Zero new `DO NOT REMOVE` markers expected.** 15-PR streak.

## Scope (in)

### Part 1 — Update the Sentry plugin config in `app.json`

Replace the plain-string entry in `plugins`:

```json
"@sentry/react-native",
```

With the array form that carries the plugin options:

```json
[
  "@sentry/react-native",
  {
    "organization": "<SENTRY_ORG_SLUG>",
    "project": "<SENTRY_PROJECT_SLUG>"
  }
],
```

To find the slugs:

- Org slug: visible in `https://sentry.io/organizations/<slug>/`. For
  the DSN currently configured (`o4511383723573248`), the org slug
  is the hyphenated name visible in the Sentry dashboard URL — Sudhir
  reads it once and gives you the value. **Do NOT guess.** Write
  the prompt with `<SENTRY_ORG_SLUG>` placeholder and have Sudhir
  fill it in before commit.
- Project slug: visible in the same URL,
  `https://sentry.io/organizations/<org>/projects/<project>/`.

Keep the existing position in the `plugins` array. The plugin reads
`SENTRY_AUTH_TOKEN` from the build env automatically — no need to
pass it via plugin options.

### Part 2 — Flip the production `SENTRY_DISABLE_AUTO_UPLOAD` flag

In `eas.json`, leave `development` and `preview` profiles alone (they
keep `SENTRY_DISABLE_AUTO_UPLOAD: "true"`). For the `production`
profile, **remove** the line entirely:

```json
"production": {
  "distribution": "store",
  "autoIncrement": true,
  "env": {
    // SENTRY_DISABLE_AUTO_UPLOAD removed — upload IS desired on prod
    "EXPO_PUBLIC_FIREBASE_API_KEY": "...",
    // ... rest of env unchanged
    "EXPO_PUBLIC_SENTRY_DSN": "..."
  },
  ...
}
```

Removing the var is cleaner than setting it to `"false"` — the
`@sentry/react-native` plugin only checks for the var's truthiness;
absence = upload enabled.

**Why prod-only:**
- Dev / preview / OTA-debug builds are throwaway. Uploading their
  maps wastes Sentry's free-tier upload quota.
- A misconfigured upload on prod fails the EAS build loudly (with
  a clear "Sentry auth failed" error from `sentry-cli`). That's a
  hard fail you'll see at build time, not a silent regression.

### Part 3 — Create the EAS secret (manual step for Sudhir)

This is the only step Windsurf cannot do — it requires an
interactive token-paste into the EAS CLI in Sudhir's terminal.
Write the exact command into the prompt so Sudhir can run it.

```text
=== SUDHIR — DO THIS IN POWERSHELL BEFORE THE NEXT PRODUCTION BUILD ===

1. Generate the Sentry auth token:
   - Visit https://sentry.io/settings/account/api/auth-tokens/
   - "Create New Token"
   - Scopes: project:releases (write), project:write
   - Name: "EAS Build - grocery-mvp-prod"
   - Copy the token (sntrys_...)

2. Create the EAS secret on the production profile only:
   eas secret:create `
     --scope project `
     --name SENTRY_AUTH_TOKEN `
     --value "<paste-the-token>" `
     --type string `
     --visibility secret `
     --environment production

3. Verify:
   eas secret:list
   # SENTRY_AUTH_TOKEN should appear with environment "production".
```

The token has org-scoped permission to upload releases; it does NOT
grant Sentry dashboard access. Treat it as you would the Firebase
service account JSON — never paste into chat, never commit.

If the token leaks, rotate immediately:

```text
eas secret:delete --id <secret-id-from-list>
# Then re-run the eas secret:create above with a fresh token.
```

### Part 4 — Test plumbing in `tests/services/sentry.test.ts`

There isn't much to unit-test about the sourcemap upload (it's a
build-time concern). But we CAN pin the runtime Sentry init contract
so a regression that silently disables Sentry doesn't escape.

Create `tests/services/sentry.test.ts`:

```ts
/**
 * PR 26 — pin the Sentry init contract.
 *
 * The sourcemap upload PR doesn't change runtime behaviour, but
 * future PRs might. These tests fail loudly if someone:
 *   - removes the DSN read from app.json
 *   - changes the prod sample rate without thinking
 *   - regresses the PII-off setting
 *   - swaps environment tags
 */
jest.mock('@sentry/react-native', () => ({
  init: jest.fn(),
}));
jest.mock('expo-constants', () => ({
  expoConfig: {
    extra: {
      sentry: {
        dsn: 'https://test@test.ingest.sentry.io/123',
      },
    },
  },
}));

const Sentry = require('@sentry/react-native');

describe('PR 26 — Sentry init contract', () => {
  beforeEach(() => {
    jest.clearAllMocks();
    jest.resetModules();
  });

  test('reads DSN from expo-constants extra.sentry.dsn', () => {
    const { initSentry } = require('../../src/services/sentry');
    initSentry();
    expect(Sentry.init).toHaveBeenCalledWith(
      expect.objectContaining({
        dsn: 'https://test@test.ingest.sentry.io/123',
      }),
    );
  });

  test('PII collection is disabled', () => {
    const { initSentry } = require('../../src/services/sentry');
    initSentry();
    expect(Sentry.init).toHaveBeenCalledWith(
      expect.objectContaining({ sendDefaultPii: false }),
    );
  });

  test('environment tag matches __DEV__ flag', () => {
    const { initSentry } = require('../../src/services/sentry');
    // __DEV__ is true in jest by default
    initSentry();
    expect(Sentry.init).toHaveBeenCalledWith(
      expect.objectContaining({ environment: 'development' }),
    );
  });

  test('Network-noise filters are present', () => {
    const { initSentry } = require('../../src/services/sentry');
    initSentry();
    const call = (Sentry.init as jest.Mock).mock.calls[0][0];
    expect(call.ignoreErrors).toEqual(
      expect.arrayContaining([
        expect.any(RegExp),
      ]),
    );
    // The /Network request failed/ pattern should still be in there.
    const hasNetwork = (call.ignoreErrors as RegExp[]).some(r =>
      r.source.includes('Network request failed'),
    );
    expect(hasNetwork).toBe(true);
  });
});
```

### Part 5 — Add a deliberate-throw helper for smoke testing

Create `src/utils/sentryDebugThrow.ts`:

```ts
/**
 * PR 26 — Dev-only helper to verify Sentry source-map upload by
 * triggering a real, de-minifiable error from a known file/line.
 *
 * Usage: temporarily wire `<Button onPress={triggerSentryTestError}>`
 * to ANY screen during smoke testing of a fresh production build.
 * Tap → app crashes / Sentry receives the event → check the Sentry
 * dashboard. The stack trace should resolve to
 * `src/utils/sentryDebugThrow.ts:<line>` rather than `<anonymous>:1`.
 *
 * REMOVE the wiring before merging. The export itself is harmless
 * to leave in place — it isn't imported anywhere by default.
 */
export function triggerSentryTestError(): void {
  // Distinct, easily-grep-able message so the corresponding Sentry
  // event is identifiable in the dashboard.
  throw new Error(
    'PR 26 — Sentry source-map upload verification crash',
  );
}
```

The file is intentionally tiny so the stack trace points
unambiguously at it.

## Smoke tests (after the NEXT production build, not the next OTA)

**Critical:** PR 26's effect only materializes when a fresh
**native** production build runs through EAS. An OTA on top of an
older native build picks up the JS changes but **doesn't trigger
the sourcemap upload** (no build = no upload step). The smoke tests
below assume a fresh `eas build --profile production` has completed.

1. **EAS build logs show the upload step** — after
   `eas build --profile production` completes, open the build's
   logs. Search for `sentry-cli`. You should see lines like:
   ```
   > Uploaded source maps to Sentry
   > Created release X.Y.Z (Z artifacts)
   ```
   If you see `SENTRY_DISABLE_AUTO_UPLOAD=true` instead, the env
   override didn't take.
2. **Sentry dashboard shows new artifacts** — visit
   `https://sentry.io/organizations/<org>/releases/`. The latest
   release should match the runtime version of the build you just
   ran. Click into it. Artifacts count > 0. Each artifact is a
   `.bundle` / `.map` pair.
3. **Test crash de-minifies** — install the new build on a phone.
   Wire `triggerSentryTestError` to any throwaway button on a
   screen (e.g. a dev-only red button at the bottom of
   `ProfileScreen` while testing). Tap it. The app crashes (RN
   error boundary). Force-close + reopen — the crash uploads from
   the on-disk queue. Within ~1 minute, the Sentry dashboard
   shows the event. **Open the stack frame.** It MUST point at
   `src/utils/sentryDebugThrow.ts:<line>` and show the function
   name `triggerSentryTestError`. If it points at
   `<anonymous>:1:24561`, the upload didn't work.
4. **No PII in the crash event** — same Sentry event. Verify the
   "User" section is empty / contains only the Sentry-generated
   anonymous ID. The phone number, email, address should NOT be
   present. (PII-off is unrelated to source maps but a good
   regression check.)
5. **Dev / preview unchanged** — run `eas build --profile preview`.
   Confirm `SENTRY_DISABLE_AUTO_UPLOAD=true` is still in the build
   env (logs will show it). Sentry should NOT receive a new release
   artifact for this build.

## Why this PR matters

Right now, when a tester reports "the app crashed", Sentry shows the
crash but we can't tell **where** in the code. Every crash
investigation starts with:

1. Open Sentry, find the event.
2. Realize the trace is minified.
3. Ask the tester to reproduce while you're watching their phone.
4. Add `console.log`s, rebuild, try again.

That's 30+ minutes per incident before any debugging actually
starts. PR 26 collapses it to:

1. Open Sentry, find the event.
2. Read the stack frame — `CheckoutScreen.tsx:327`.
3. Open the file. Diagnose. Fix.

Multiplied across every production crash for the next six months,
this is one of the highest-value 30-minute investments on the
roadmap. And it's a one-shot config change — once it's on, it
stays on for every future build.

Also: in the Phase A push to family-test → public launch, the
volume of unfamiliar device / Android-OEM crashes goes up sharply.
Without source maps, that volume becomes a noise floor we can't
debug through.
