# PR 42.1 — Separate shop + delivery partner ratings (Windsurf prompt)

> Naming note: this is PR 42.1 because Sudhir labeled it that in
> the May 26 2026 decision conversation, but architecturally it's
> independent of PR 42 (storefront wiring). They can ship in
> either order — there's no code dependency between them. If
> renaming feels cleaner later, this is fine to call PR 45 too.

## Why this PR exists

Today the customer rating system (PR 20) compresses **shop quality**
(freshness, packaging accuracy, item availability) and **delivery
quality** (timeliness, courtesy, condition on arrival) into a
single 1-5 star rating, all of which flows to `shop.ratingAvg`.
This is wrong in two directions:

1. **Bad delivery experience tanks the shop's rating unfairly.**
   The shop owner controls product quality but not whether the
   delivery partner arrived 25 minutes late. Today a 2-star
   review for "took forever to arrive" punishes Sharma Kirana
   Store's standing on the home screen.
2. **Good delivery has no surface to be recognized.** Delivery
   partners have no rolling-average reputation. Admin can't tell
   which partners are reliable; can't deprioritize chronically
   late partners; can't reward consistent performers.

Industry standard for food/grocery delivery (Swiggy, Zomato,
Blinkit, Instamart, Uber Eats, etc.) is **two ratings per order**:
one for the shop, one for the delivery partner. Customers
already expect this UX from other apps; the single-rating model
in HamaraSetu reads as missing functionality, not as a deliberate
choice.

PR 42.1 splits the rating into two:

- Customer rates the **shop** (1-5 stars + optional comment).
- Customer rates the **delivery partner** (1-5 stars + optional
  comment). Optional — if customer skips, only shop rating
  submits. (Some orders won't have a delivery partner attached
  if the flow is interrupted; the UI must handle that.)

This is **not pilot-blocking** but **should ship before shop #2
onboards**. Reason: once you have multiple shops in the system,
historical rating data starts to matter — and you don't want
shop #1's existing single-stars data co-mingled with shop #2's
new dual-stars data in a way that distorts comparisons. Cleaner
to flip everyone to the dual model before the cohort grows.

## Scope of changes

### A. Schema additions (additive, no migration of existing data)

`src/types/index.ts` — extend `Order`:

```ts
export type Order = {
  // ... existing fields ...

  // PR 20 single-rating fields. Kept as historical for orders
  // rated before PR 42.1. New orders write to shopRating /
  // deliveryRating instead.
  rating?: 1 | 2 | 3 | 4 | 5;
  ratingComment?: string;

  // PR 42.1 — separate shop + delivery ratings.
  shopRating?: 1 | 2 | 3 | 4 | 5;
  shopComment?: string;

  // Delivery rating is optional even when other ratings are
  // submitted — if the customer didn't see the delivery
  // partner (gate-handoff, e.g.) they may legitimately skip
  // this dimension.
  deliveryRating?: 1 | 2 | 3 | 4 | 5;
  deliveryComment?: string;
};
```

`User` type (in `src/types/index.ts` and `functions/src/types.ts`
if separate) — add delivery rolling-avg fields:

```ts
export type User = {
  // ... existing fields ...

  // PR 42.1 — rolling delivery partner rating. Only populated
  // for users with isDelivery === true; ignored for everyone
  // else. Mirrors shop.ratingAvg / ratingCount pattern.
  deliveryRatingAvg?: number;
  deliveryRatingCount?: number;
};
```

**No migration of existing orders.** Orders with
`rating: <number>` keep that field as the historical record.
New ratings written post-PR-42.1 write to `shopRating` /
`deliveryRating` exclusively. The server treats either field
as "already rated" for the submit-once policy.

**`shop.ratingAvg` / `ratingCount` semantics unchanged.** They
continue to be the rolling average. After PR 42.1, only
`shopRating` (not the combined single rating) feeds into them.
This means the existing single-rating data history still drives
the shop's rolling average up to the PR 42.1 cutover.

### B. Pure helper updates in `functions/src/ratingHelpers.ts`

Replace `validateRatingSubmission` to accept the new dual-rating
shape AND retain backwards-compat for the legacy single-stars
shape (in case any not-yet-OTA'd client still sends the old
payload during the deploy transition window):

```ts
export type SubmitDualRatingInput = {
  auth: { uid: string } | null | undefined;
  order:
    | {
        customerUid?: unknown;
        status?: unknown;
        // Order is "already rated" if EITHER the legacy
        // single-rating field OR the new shopRating field is
        // populated. The submit-once policy spans both schemas.
        rating?: unknown;
        shopRating?: unknown;
        shopId?: unknown;
        deliveryPersonId?: unknown;
      }
    | null
    | undefined;

  // Either:
  //   - Legacy single-rating shape: stars + comment
  //   - New dual-rating shape: shopRating + shopComment? +
  //     deliveryRating? + deliveryComment?
  //
  // The helper detects which shape was sent. Tests pin both
  // paths.
  stars?: unknown;        // legacy
  comment?: unknown;      // legacy
  shopRating?: unknown;   // new
  shopComment?: unknown;  // new
  deliveryRating?: unknown;  // new — optional
  deliveryComment?: unknown; // new — optional
};

export type SubmitDualRatingResult =
  | {
      ok: true;
      uid: string;
      shopId: string;
      // For legacy callers: stars is the shop rating.
      // For new callers: shopRating is the shop rating.
      // Server normalises to shopRating in the result so the
      // callable doesn't have to branch.
      shopRating: 1 | 2 | 3 | 4 | 5;
      shopComment?: string;
      // Present only if delivery rating was submitted AND order
      // has a deliveryPersonId. If either is missing, server
      // skips the delivery-side write but still accepts the
      // shop rating.
      deliveryRating?: 1 | 2 | 3 | 4 | 5;
      deliveryComment?: string;
      deliveryPersonId?: string;
    }
  | { ok: false; code: ...; message: string };
```

Layered checks (cheapest first):

1. auth + order existence — unchanged from PR 20.
2. customer uid matches — unchanged.
3. `order.status === 'delivered'` — unchanged.
4. **Submit-once span:** if `order.rating` OR `order.shopRating`
   is set → already rated. New rejection message:
   "This order has already been rated."
5. `order.shopId` present — unchanged.
6. **Shape detection:** if `input.shopRating !== undefined` →
   new path. Else if `input.stars !== undefined` → legacy path,
   coerce to shopRating; ignore delivery fields. Both shape
   detections enforce range 1-5 + integer.
7. **Delivery rating (new path only):** if
   `input.deliveryRating !== undefined`, validate range 1-5 +
   integer AND require `order.deliveryPersonId` to be a
   non-empty string. If deliveryPersonId is missing, accept the
   shop rating but log a warning + drop the delivery rating
   (don't fail the whole submission).
8. Comment length checks for both `shopComment` and
   `deliveryComment` — same 500 char cap as PR 20's
   single-comment.

Keep `computeNewRollingAverage` unchanged — it's pure, single
purpose, reused for both shop and delivery aggregates.

### C. Update `submitOrderRating` callable in
`functions/src/index.ts`

The callable becomes a multi-write transaction:

```ts
export const submitOrderRating = onCall<{
  orderId: string;
  // Legacy single-rating shape (still accepted)
  stars?: number;
  comment?: string;
  // New dual-rating shape
  shopRating?: number;
  shopComment?: string;
  deliveryRating?: number;
  deliveryComment?: string;
}>(
  { cors: true, enforceAppCheck: false },
  async request => {
    // ... fetch order + validate via the extended pure helper
    const result = validateDualRatingSubmission({ ... });
    if (!result.ok) throw new HttpsError(result.code, result.message);

    // Atomic transaction — order doc + shop doc + (optional)
    // delivery partner user doc all update together. If any
    // one fails, none commit.
    await db.runTransaction(async tx => {
      // ... order read ...

      // Update the order doc with the dual-rating fields
      tx.update(orderRef, {
        shopRating: result.shopRating,
        shopComment: result.shopComment ?? null,
        deliveryRating: result.deliveryRating ?? null,
        deliveryComment: result.deliveryComment ?? null,
        updatedAt: FieldValue.serverTimestamp(),
      });

      // Update shop rolling average
      const shopSnap = await tx.get(shopRef);
      const { newAvg: shopAvg, newCount: shopCount } =
        computeNewRollingAverage(
          shopSnap.data()?.ratingAvg,
          shopSnap.data()?.ratingCount,
          result.shopRating,
        );
      tx.update(shopRef, {
        ratingAvg: shopAvg,
        ratingCount: shopCount,
      });

      // Update delivery partner rolling average (only if both
      // a delivery rating was submitted AND the order has a
      // deliveryPersonId)
      if (result.deliveryRating && result.deliveryPersonId) {
        const userRef = db.doc(`users/${result.deliveryPersonId}`);
        const userSnap = await tx.get(userRef);
        const { newAvg: dAvg, newCount: dCount } =
          computeNewRollingAverage(
            userSnap.data()?.deliveryRatingAvg,
            userSnap.data()?.deliveryRatingCount,
            result.deliveryRating,
          );
        tx.update(userRef, {
          deliveryRatingAvg: dAvg,
          deliveryRatingCount: dCount,
        });
      }
    });

    return { ok: true };
  },
);
```

**Backwards-compat is load-bearing.** During the OTA window
between server deploy and client update propagation, some
clients will still send `{ stars, comment }`. The callable
must accept that shape and treat it as a shop-only rating.

### D. Client UI — split `RateOrderCard` into dual rating

`src/components/order/RateOrderCard.tsx`:

Two-section card OR two stacked sub-cards (designer's choice on
layout — both work; same form, just visual treatment). Each
section has:

- Heading ("How was the shop?" / "How was your delivery?")
- 5-star tap picker
- Optional comment input with live counter (500 char cap)

The shop section is **required** to submit. The delivery
section is **optional** — but only if the order has a
`deliveryPersonId` should the delivery section render at all.
For orders with `deliveryPersonId === null` (rare — only if the
order never got picked up before being delivered some other
way), hide the delivery section entirely and just show the shop
rating.

State shape:

```ts
const [shopStars, setShopStars] = useState<0 | 1 | 2 | 3 | 4 | 5>(0);
const [shopComment, setShopComment] = useState('');
const [deliveryStars, setDeliveryStars] = useState<0 | 1 | 2 | 3 | 4 | 5>(0);
const [deliveryComment, setDeliveryComment] = useState('');
const [submitting, setSubmitting] = useState(false);
```

Submit button enabled only when `shopStars >= 1` AND not
submitting. Delivery section stars 0 means "skipped" — server
treats undefined deliveryRating as skip.

On submit:

```ts
await orderService.submitOrderRating({
  orderId,
  shopRating: shopStars,
  shopComment: shopComment.trim() || undefined,
  deliveryRating: deliveryStars > 0 ? deliveryStars : undefined,
  deliveryComment: deliveryStars > 0
    ? (deliveryComment.trim() || undefined)
    : undefined,
});
onRated(/* updated props */);
```

The `onRated` callback (used by OrderDetailScreen to flip to the
"Thanks for rating!" view) should pass enough info that the
post-rating state can display both ratings, e.g.:

```ts
type OnRatedPayload = {
  shopRating: 1 | 2 | 3 | 4 | 5;
  shopComment?: string;
  deliveryRating?: 1 | 2 | 3 | 4 | 5;
  deliveryComment?: string;
};
```
