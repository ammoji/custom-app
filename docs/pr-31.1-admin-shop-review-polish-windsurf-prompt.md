# PR 31.1 — Admin shop-review polish (Windsurf prompt)

## Why this PR exists

During PR 31 smoke testing, three small admin-UX gaps surfaced.
None of them are bugs in PR 31 itself — they're pre-existing
limitations that became more obvious now that real shops are
actually going through the review flow. All three live in the
admin shop-review surface; all three are small.

1. **Lat/lng coords are not actionable.** Admin sees
   `📍 38.9897, -90.6879` as plain text in both
   `ShopRegistrationDetailScreen` (pending review) and
   `ShopDetailManagementScreen` (post-approval / rejected /
   suspended). To verify the location, admin has to manually
   copy-paste the coords into Google Maps. Should be one tap.
2. **Rejection reason is invisible to admin.** When a shop is
   rejected, `rejectedReason` lands on the shop doc and is
   already surfaced to the owner in `WaitingForApprovalScreen`
   (line ~227). But the admin's "Rejected" view in
   `ShopDetailManagementScreen` only says "Rejected shops have
   no available actions" — no history of why or when.
3. **KYC docs vanish after approval.** PR 31's KYC docs grid
   only renders in `ShopRegistrationDetailScreen` (the pending-
   review screen). Once a shop is approved, the admin moves to
   `ShopDetailManagementScreen` for ongoing management and the
   docs become inaccessible from the UI. The server-side
   `getShopKycReadUrls` callable has no status restriction —
   it works for any shop the admin can see — so this is
   purely a wiring gap.

**PR 31.1 closes all three on the admin side.** Pure client +
small UI surface. No server changes. No callable changes. No
rules changes. OTA-only.

~1–1.5 hours.

## Critical lessons from PRs 25, 27, 31 (do not repeat)

1. **Never strip imports between edits in the same PR.** Three
   screens touched (the two admin screens + a new utility). Each
   gets a small import addition (`Linking`, `openMapsForCoords`,
   or the existing `Pressable`). Keep imports stable.
2. **All `useState` calls in screens sit ABOVE conditional early
   returns.** `ShopDetailManagementScreen` already has a
   "fetching / not found" early return — the new KYC-docs
   `useState` + `useEffect` must sit above it (mirror the
   pattern in `ShopRegistrationDetailScreen` where PR 31
   added the docs viewer).
3. **OTA-only deploy.** No server changes. Skip the server-first
   ordering — go straight to `eas update --branch production`
   after tests pass.
4. **Don't re-architect existing screens.** PR 31.1 is additive
   — three small additions, zero existing-pattern changes.
   Especially: don't touch the existing `registrationData` card
   layout, don't refactor the rejected-shops branch into a
   helper, don't promote `openMapsForCoords` to a hook. The
   smallest defensible change is the right change.
5. **Zero new `DO NOT REMOVE` markers expected.** No imports
   are at risk; no protective markers needed.

### Part 1 — `openMapsForCoords` utility

Create `src/utils/openMapsForCoords.ts`:

```ts
import { Linking, Platform } from 'react-native';

/**
 * PR 31.1 — open a coordinates pair in the device's preferred
 * maps app via the universal Google Maps deep link.
 *
 * Web: opens in a new tab via Linking.openURL (which maps to
 *   window.open) — no need for expo-web-browser; Maps is
 *   universally available.
 * Native: opens the Google Maps app if installed (iOS + Android
 *   both register the `https://www.google.com/maps?...` URL
 *   scheme), else falls back to the browser. iOS users with
 *   Apple Maps as default still get the link rendered by Apple
 *   Maps on tap if they prefer — universal URL.
 *
 * The `(0, 0)` sentinel — used by `registerShop` when GPS was
 * unavailable at registration — is treated as "no location" by
 * the caller, NOT here. This utility just opens whatever it's
 * given.
 *
 * Sentry-quiet: `Linking.openURL` rejection is swallowed and
 * console-warned, never thrown to the caller. A failed open is
 * not actionable from the UI — the caller has no recovery path.
 */
export async function openMapsForCoords(
  lat: number,
  lng: number,
  label?: string,
): Promise<void> {
  // Google's universal maps URL: works on iOS, Android, and web.
  // `q=<lat>,<lng>(<label>)` shows a labelled pin if a label is
  // provided; otherwise just the coords.
  const query = label
    ? `${lat},${lng}(${encodeURIComponent(label)})`
    : `${lat},${lng}`;
  const url = `https://www.google.com/maps?q=${query}`;

  try {
    await Linking.openURL(url);
  } catch (e) {
    // Should be unreachable on platforms we ship — every browser
    // and the Maps app on both mobile OSes registers the
    // https://www.google.com/maps URL pattern. Log defensively
    // so a phantom failure shows up in dev console without
    // surfacing to the user.
    // eslint-disable-next-line no-console
    console.warn('[openMapsForCoords] Linking.openURL failed:', e);
  }
}
```

No new deps. No `expo-web-browser` indirection — that helper is
for legal/in-app browsing; maps want the user to leave the app
and pick their preferred handler.

useEffect(() => {
  if (!isAdmin || !shopId) {
    setKycLoading(false);
    return;
  }
  let cancelled = false;
  orderService
    .getShopKycReadUrls({ shopId })
    .then(({ urls }) => {
      if (!cancelled) setKycUrls(urls);
    })
    .catch(e => {
      console.warn('[ShopDetailManagement] getShopKycReadUrls failed:', e);
    })
    .finally(() => {
      if (!cancelled) setKycLoading(false);
    });
  return () => {
    cancelled = true;
  };
}, [isAdmin, shopId]);

## Why this PR matters

Three small admin-UX gaps individually, but together they're the
difference between "admin can review a shop in 30 seconds" and
"admin has to copy-paste coords, hunt for rejection history in
Audit Log, and re-pull docs out of Cloud Storage by hand." The
first version is sustainable as the shop count grows to 100+;
the second isn't.

The KYC-docs-post-approval gap is the most important — once we
have real shops, customer disputes ("this shop scammed me",
"these are fake credentials") will require pulling KYC evidence
from the original onboarding. If those docs are only visible
during the pending-review window, admin has to query Cloud
Storage manually after approval, which is slow and error-prone.

PR 31.1 closes the loop on PR 31. Three small additions, zero
existing-pattern changes, OTA-only deploy. Same-day shippable.
