# PR 36.2 — Reset pilot data script (reusable destructive cleanup, keep users) (Windsurf prompt)

## Why this PR exists

During pilot prep + pilot itself, we'll need to reset test
data more than once: between major test cycles, when
onboarding a new test shop, before pilot starts, between
pilot phases. The existing `scripts/reset-test-data.ts`
nukes everything (orders + shops + menus + **users + auth**)
which is too heavy for most cleanup needs.

PR 36.2 ships a **second destructive cleanup script** —
`scripts/reset-pilot-data.ts` — that keeps the user data
(profiles + auth accounts) intact and wipes everything else.
After running it, the project is in a "clean app, ready to
onboard from scratch" state where existing test users can
sign back in as customers and re-go-through the full
onboarding flow.

**Why a second script (instead of extending the existing one
with a flag):** the semantics are different enough that a
single script with conditional behaviour gets confusing fast.
`reset-test-data.ts` is "wipe everything including users —
nuke from orbit." `reset-pilot-data.ts` is "wipe content but
keep accounts — clean app, same testers." Two scripts, two
clear intents, fewer footguns.

**What ships:**

- `scripts/reset-pilot-data.ts` — main entry. Thin wiring
  layer around the helpers.
- `scripts/reset-pilot-data.helpers.ts` — pure logic
  (allowlist guard, planning, flag parser). Reuses
  `ALLOWED_PROJECTS` and the admin-protection patterns from
  the existing `reset-test-data.helpers.ts`.
- `tests/scripts/reset-pilot-data.test.ts` — unit tests for
  the pure helpers.
- `package.json` script alias: `npm run reset:pilot-data`
  (dry-run) and `npm run reset:pilot-data -- --execute` (do
  it).

~2 hours Windsurf work. **No deploy involved** — this is a
local tool. Committed but not pushed via OTA.

## Critical lessons from the existing script (mirror them)

1. **Project allowlist is hardcoded.** Never accept the
   target project from a flag or env var. Reuse the
   existing `ALLOWED_PROJECTS = ['grocery-mvp-dev']` from
   `reset-test-data.helpers.ts`.
2. **Dry-run by default; `--execute` to actually delete.**
   This is the single biggest safety guard against muscle
   memory mistakes.
3. **Confirmation prompt unless `--yes` flag.** Even with
   `--execute`, the operator should be asked to type
   "DELETE" or similar before the wipe runs.
4. **Per-collection batch deletes, max 500 per batch.**
   The existing `deleteRefsInBatches` helper handles this;
   either reuse via import or copy the pattern.
5. **Audit log written per run.** JSON file at
   `scripts/.cleanup-logs/{timestamp}-pilot.json` recording
   what was deleted + any failures. The `.gitignore`
   already excludes `scripts/.cleanup-logs/*` so logs
   don't pollute the repo.
6. **Service account UID is the admin to preserve.** The
   existing script protects `ADMIN_PROTECT_UID` (passed via
   env var or detected from the service account). Mirror
   this — the new script must NEVER revoke the admin user's
   role claim.
7. **No `DO NOT REMOVE` markers expected.** Pure tooling
   addition.

### Part 1 — `scripts/reset-pilot-data.helpers.ts` (pure logic)

Re-export the allowlist + admin-protection helpers from the
existing module:

```ts
/**
 * Pure helpers for scripts/reset-pilot-data.ts.
 *
 * Companion to scripts/reset-test-data.helpers.ts — that one
 * protects against accidental full-nuke; this one against
 * accidental keep-users-only nuke. Same safety posture, same
 * allowlist, different deletion plan.
 */

// Re-export from the existing helpers so the allowlist stays
// a single source of truth.
export {
  ALLOWED_PROJECTS,
  assertProjectAllowed,
  type AllowedProject,
} from './reset-test-data.helpers';

// -------------------------------------------------------------------
// Flag parser
// -------------------------------------------------------------------

export type ResetPilotFlags = {
  execute: boolean;
  yes: boolean; // skip the interactive confirmation
  skipStorage: boolean; // omit Storage cleanup (useful in tests)
};

export function parseFlags(argv: string[]): ResetPilotFlags {
  return {
    execute: argv.includes('--execute'),
    yes: argv.includes('--yes'),
    skipStorage: argv.includes('--skip-storage'),
  };
}

// -------------------------------------------------------------------
// Collections to wipe
// -------------------------------------------------------------------

/**
 * The collections this script deletes. Order matters when there
 * are FK-style references — orders should go before refunds in
 * theory, but at our scale it doesn't matter because we're
 * wiping both. Listed in alphabetical order for stability.
 *
 * NOT in this list (kept intentionally):
 *   - users        — keep all auth + profile data
 *   - aiFeatures   — keep kill-switch docs (menuExtraction.enabled,
 *                     voiceOnboarding.enabled)
 *
 * If a future collection is added (e.g., shops/{id}/khata when
 * PR 37 un-defers), it needs to be added here. The list is
 * unit-tested for completeness against firestore.rules so a
 * forgotten addition fails CI.
 */
export const COLLECTIONS_TO_WIPE = [
  'aiAuditLog',
  'aiQuotas',
  'auditLog',
  'deliveryRequests',
  'featureUsageLog',
  'orders',
  'pendingShopRequests',
  'products',
  'razorpayWebhookEvents',
  'refunds',
  'shops', // includes subcollections: menu, kycDocs references
] as const;

export type WipeCollectionName = (typeof COLLECTIONS_TO_WIPE)[number];

export const PROTECTED_COLLECTIONS = ['users', 'aiFeatures'] as const;

// -------------------------------------------------------------------
// Storage paths to wipe
// -------------------------------------------------------------------

export const STORAGE_PATHS_TO_WIPE = [
  'shop-kyc/', // PR 31 KYC document uploads
  'menu/',     // PR 6.1 menu item image uploads
] as const;

// -------------------------------------------------------------------
// User role-claim cleanup planning
// -------------------------------------------------------------------

/**
 * Given a list of user docs + the admin UID, return the UIDs
 * that should have their shop-owner / delivery role claims
 * revoked. The admin user is never in the returned list.
 *
 * A user is included if they have ANY of:
 *   - users/{uid}.isShopOwner === true
 *   - users/{uid}.isDelivery === true
 *   - users/{uid}.shopId !== null and !== undefined
 *
 * (Custom claims are checked separately by the auth-side
 * cleanup; this just plans the Firestore-side fields list.)
 */
export type UserDocSnapshot = {
  uid: string;
  isShopOwner?: boolean;
  isDelivery?: boolean;
  shopId?: string | null;
};

export function planUserRoleCleanup(
  users: UserDocSnapshot[],
  adminUid: string,
): {
  uidsToClean: string[];
  fieldsToRemove: ReadonlyArray<'isShopOwner' | 'isDelivery' | 'shopId' | 'favorites'>;
} {
  if (!adminUid) {
    throw new Error(
      'planUserRoleCleanup: adminUid required (set ADMIN_PROTECT_UID)',
    );
  }
  const uidsToClean = users
    .filter(u => u.uid !== adminUid)
    .filter(
      u =>
        u.isShopOwner === true ||
        u.isDelivery === true ||
        (u.shopId !== null && u.shopId !== undefined),
    )
    .map(u => u.uid);

  // Same fields always; the function returns a constant so the
  // caller has one source of truth.
  const fieldsToRemove = [
    'isShopOwner',
    'isDelivery',
    'shopId',
    'favorites',
  ] as const;

  return { uidsToClean, fieldsToRemove };
}
```

Lines of code: ~120 — small, all pure, all testable.

### Part 2 — `scripts/reset-pilot-data.ts` (main entry)

Mirror the structure of `scripts/reset-test-data.ts`. Key
differences:

```ts
/**
 * Destructive cleanup script — keeps users + auth, wipes
 * everything else (shops, orders, products, related payment
 * data, all analytics/audit collections, and the Storage
 * folders for KYC + menu images).
 *
 *   npm run reset:pilot-data               # dry-run (default)
 *   npm run reset:pilot-data -- --execute  # actually delete
 *   npm run reset:pilot-data -- --execute --yes   # skip prompt
 *   npm run reset:pilot-data -- --execute --skip-storage  # firestore only
 *
 * Companion to scripts/reset-test-data.ts — that one nukes
 * everything including users. This one preserves users so
 * existing test accounts can sign back in as fresh customers
 * after the wipe.
 *
 * Safety guards:
 *   - Project allowlist (ALLOWED_PROJECTS — grocery-mvp-dev only)
 *   - Admin UID protection (ADMIN_PROTECT_UID env var; falls
 *     back to service-account.json's client_email lookup)
 *   - Dry-run by default
 *   - Interactive "type DELETE to confirm" unless --yes
 *   - Audit log at scripts/.cleanup-logs/{timestamp}-pilot.json
 *
 * Per .windsurf/test-discipline.md: tests for the pure helpers
 * pin the dangerous edges; the rest of main() is firebase-admin
 * glue proven by dry-run smoke.
 */
```

The body of the script:

1. **Load service account + validate project.** Same pattern
   as the existing script — read `service-account.json`, call
   `assertProjectAllowed(serviceAccount.project_id)`.

2. **Initialize firebase-admin.** Use the same `cert(...)` +
   `initializeApp({ credential, storageBucket })` pattern.
   `storageBucket: '<project-id>.firebasestorage.app'`.

3. **Determine admin UID to protect.** Read from
   `process.env.ADMIN_PROTECT_UID`. If absent, look up the
   admin by querying `users` collection for
   `isAdmin == true` AND `phoneNumber == <known admin phone>`
   — match the existing script's detection logic. **If
   detection fails, abort with a clear error** ("set
   ADMIN_PROTECT_UID to <uid>").

4. **Plan phase (always runs):**
   - For each collection in `COLLECTIONS_TO_WIPE`, count
     documents.
   - For `shops`, also count nested `menu` subcollection docs.
   - For each Storage path in `STORAGE_PATHS_TO_WIPE`, list
     files (paginate if needed; just count for the plan).
   - Walk `users` collection, build `UserDocSnapshot[]`, call
     `planUserRoleCleanup` to get the list of UIDs needing
     claim revocation.
   - Print a colored summary:

     ```
     ┌─ RESET PILOT DATA — PLAN ───────────────
     │ Project:      grocery-mvp-dev ✓
     │ Admin UID:    NB452wQTy... (preserved) ✓
     │
     │ Collections to wipe:
     │   shops              12 docs (+ 47 menu subdocs)
     │   orders             89 docs
     │   refunds            14 docs
     │   ...
     │
     │ Storage to wipe:
     │   shop-kyc/          22 files (3.8 MB)
     │   menu/              31 files (5.2 MB)
     │
     │ User cleanup:
     │   users to keep:     5 (incl. admin)
     │   role claims to revoke from: 2 non-admin users
     └─────────────────────────────────────────
     ```

5. **If dry-run, exit here.** Print "DRY RUN — no changes
   made. Re-run with --execute to actually delete." Audit log
   IS still written (plan-only entry) for traceability.

6. **If --execute and NOT --yes:** prompt for typed
   confirmation:

   ```
   This will permanently delete the above. Type DELETE to confirm:
   ```

   Anything other than `DELETE` (case-sensitive) aborts.

7. **Execute phase:**

   a. **Firestore collections** — for each in
      `COLLECTIONS_TO_WIPE`, query all docs, batch-delete in
      500s. Reuse `deleteRefsInBatches` pattern from the
      existing script. For `shops`, also descend into each
      shop's `menu` subcollection before deleting the parent.
      If PR 37 ever un-defers, `khata` subcollection becomes
      another descent — add to the list in
      COLLECTIONS_TO_WIPE planning logic at that point.

   b. **Storage** (if not `--skip-storage`) — use
      `admin.storage().bucket().deleteFiles({ prefix: 'shop-kyc/' })`
      and same for `menu/`. Each call is async + handles
      paginated deletes internally.

   c. **User role cleanup** — for each UID in
      `planUserRoleCleanup`'s result:
      - **Firestore:** update `users/{uid}` to delete fields
        `isShopOwner`, `isDelivery`, `shopId`, `favorites`
        via `FieldValue.delete()`.
      - **Auth claims:** call
        `admin.auth().getUser(uid)` → read current claims →
        build new claims preserving `admin: true` if present,
        dropping `shopOwner`, `shopId`, `delivery` → call
        `admin.auth().setCustomUserClaims(uid, newClaims)`.
      - Sleep ~50 ms between users to avoid hitting Auth
        rate limits if there are 100+ users.

8. **Write audit log** to `scripts/.cleanup-logs/{ISO-timestamp}-pilot.json`
   with the full counts, the UIDs affected, any failures.
   Print the log path on completion.

9. **Print summary** + exit cleanly.

## Scope (out)

- **Cross-project execution.** Allowlist is hardcoded to
  `grocery-mvp-dev`. If prod ever needs a similar tool, that's
  a separate PR with a separate allowlist + separate review.
- **Selective collection wipes.** Currently the script wipes
  the full COLLECTIONS_TO_WIPE list. If a future need arises
  for "wipe only orders" or "wipe only analytics," extend with
  a `--only <name1>,<name2>` flag in a follow-up. v1 keeps
  the scope simple.
- **Restoring from backup.** Out of scope; this is a
  delete-only tool. If you wipe by mistake, the only recovery
  is Firestore PITR (point-in-time recovery), which is a
  separate Firebase feature.
- **Storage restore.** Same — wiped files are gone unless
  Firebase Storage versioning is enabled.
- **Custom user filtering.** All non-admin users with
  shop/delivery roles get their claims revoked. No
  "keep this specific test user as a shop owner" option.
  Simpler model: after running the script, anyone who wants
  to be a shop owner again re-registers via the app.

## Why this PR matters

Two sentences:

The existing `reset-test-data` script is too heavy (nukes
users + auth too), and copy-pasting 11 separate `firebase
firestore:delete` commands every time we want a fresh test
state is error-prone + slow. PR 36.2 ships a single
`npm run reset:pilot-data -- --execute` that puts the app in
the exact state pilot needs: clean data, same testers,
ready to onboard from scratch.

It's also a permanent capability for post-pilot ops: if you
ever want to "reset to clean app state but keep our user
list" — e.g., before a pilot phase 2, before a demo, before
an investor review — that's one command. Worth the ~2 hours.
