# PR 32.2 — Force PNG on category placeholder URLs (RN-can't-render-SVG fix) (Windsurf prompt)

## Why this PR exists

PR 32.1 shipped 10 category-themed placeholder URLs via
placehold.co. Server-side verified working — items land in
Firestore with the correct per-category URL. Smoke testing on
device, however, revealed every placeholder rendering as an
empty box.

**Root cause: placehold.co serves SVG by default for URLs that
don't specify a format.** React Native's `<Image>` component
**cannot render SVG natively** (it handles PNG / JPG / GIF /
WebP only). When RN's image loader hits an SVG response, it
silently fails — no error, no fallback, just empty space where
the image should be.

**The fix is a 10-character edit per URL: add `.png` after the
size segment** to force placehold.co to serve PNG.

| Before (PR 32.1) | After (PR 32.2) |
|---|---|
| `https://placehold.co/400x400/F5E6D3/8B4513?text=...` | `https://placehold.co/400x400.png/F5E6D3/8B4513?text=...` |

Once the 10 URLs in `CATEGORY_PLACEHOLDER_URLS` are updated and
the two callables that use the helper are redeployed, every NEW
menu item gets the PNG-flavor URL and renders correctly.

**Existing items in Firestore retain the SVG-flavor URL** and
will continue to render as empty boxes. For pilot, the cleanest
move is to delete + re-scan the small handful of test items
already in the menu (Option A per the conversation that
produced this PR). A backfill script is intentionally out of
scope — at pilot scale (~10–30 items per test shop), manual
delete + re-scan is faster than writing + reviewing a backfill.

~30 minutes Windsurf work. Server-only deploy (no client
changes; no native rebuild; no rules; no secrets). OTA push
optional (no client code changed; OTA only carries the docs).

## Critical lessons from PRs 25–36.1 (do not repeat)

1. **`<Image>` in React Native renders PNG/JPG/GIF/WebP only.**
   Any placeholder service URL needs to be explicit about the
   image format. placehold.co's default of SVG is fine for
   browsers but invisible in RN. **Permanent rule worth adding
   to `.windsurf/code-discipline.md` (do this in Part 4
   below).**
2. **Server-only deploy.** Two callables redeploy
   (`addCustomMenuItem`, `addExtractedMenuItems`). No client
   changes; the URL value just flows through the existing
   `imageUrl` field. OTA strictly not required but push one
   anyway for the docs + PRELAUNCH update.
3. **Never strip imports between edits.** Single file
   modified for code; this PR has trivial scope for stripping
   risk.
4. **Schema-additive only.** PR 32.2 doesn't change any
   document shape; it changes the URL value written into the
   existing `imageUrl` string field. Pre-PR-32.2 items keep
   their old URL; post-PR-32.2 items get the new URL.
5. **No new `DO NOT REMOVE` markers expected.**

### Part 4 — Add the RN+SVG lesson to code-discipline.md

In `.windsurf/code-discipline.md`, append a new section after
the existing rules:

```markdown
## Rule 7 — Image URLs for React Native must specify a raster format

React Native's `<Image>` component renders PNG, JPG, GIF, and
WebP. **It does NOT render SVG.** Any external URL that might
serve SVG (placehold.co, some CDNs that do content negotiation,
SVG icon sets) must specify a raster format explicitly:

- placehold.co: add `.png` after the size segment, e.g.
  `https://placehold.co/400x400.png/F5E6D3/8B4513?text=...`
- Other placeholder services: check their docs for the
  format query param or path segment
- Icon CDNs: prefer `.png` exports over the SVG default

When writing or reviewing any PR that adds external image URLs,
verify the format is explicit. The failure mode is silent —
RN's <Image> renders nothing, logs nothing, captures nothing
in Sentry. The bug only surfaces on visual inspection of the
device.

**First instance:** PR 32.1 shipped category placeholders with
SVG-flavor URLs; every placeholder rendered as empty box.
PR 32.2 fixed it by adding `.png` to each URL. Discipline
note added so future placeholder/icon work doesn't recur.
```

## Scope (out)

- **Backfill of existing items** with the SVG-flavor URL.
  At pilot scale (~30 items), manual delete + re-scan is
  faster than coding a backfill. If scale grows OR shops
  report broken images on a per-item basis, the backfill is
  a 30-min one-shot script that walks
  `collectionGroup('menu').where('imageUrl', '>=', '...').get()`,
  rewrites the URL via string-replace, writes back.
  Documented in PRELAUNCH but NOT shipped here.
- **Client-side fallback rendering** when an image fails to
  load (an `<Image onError={...} defaultSource={...} />`
  pattern). Would mask the bug rather than fix it; if the
  PNG fix doesn't resolve the visible problem we'd
  investigate why placehold.co's PNG endpoint is unreachable,
  not paper over with a generic fallback. Out of scope for
  this PR.
- **Switching placeholder providers** (e.g., to a
  pre-generated set of PNG assets hosted on Firebase
  Storage). More work, no clear benefit at pilot scale.
  The placehold.co .png URLs are stable and free; revisit
  only if the service rate-limits or has reliability issues.

## Why this PR matters

PR 32.1 was *visually broken* at the moment of pilot — every
new menu item rendered as a blank rectangle. That's worse than
the original generic-placeholder state because at least the
generic placeholder was *something visual*. Shopkeepers who
scan a 60-SKU rate-list see 60 empty boxes, which signals
"this app is broken" much harder than "this app is generic."

PR 32.2 unbreaks the visual at the absolute minimum scope —
one tiny change to one file, one redeploy. The discipline-doc
addition (Rule 7) ensures this exact class of bug doesn't recur
in any future PR that touches external image URLs.

This is the smallest-impact PR in the whole pilot prep, and
also the one that materially affects whether a customer's
first impression of a freshly-onboarded shop is "looks
organized" or "looks broken." Worth the 30 minutes.
