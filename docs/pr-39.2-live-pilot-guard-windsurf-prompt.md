# PR 39.2 — Live-pilot guard on all three reset scripts

**Source:** Pre-pilot must-do, called out as the pilot-launch lock in `CLAUDE.md` In-flight work and `PROMPT_AUTHORING_NOTES.md`. Once shop #1 takes a real money order, an accidental `npm run reset:test-data -- --execute` could destroy live customer data. The existing safety guards (project allowlist, admin UID protection, dry-run default, typed DELETE confirm, audit log) are necessary but not sufficient — none of them notice that the project they're targeting now contains real customer orders instead of test data.

**Design lens — operator's mistake we're preventing:**
*"I forgot pilot started Monday. I'm running my usual `reset:test-data` to clean up before a demo. The script runs. Shop #1's customer just lost their order history."*

The fix: a Firestore flag `appConfig/pilotStatus.isLive` that all three reset scripts read at startup. When `true`, the script refuses with a loud banner — even with `--execute --yes` passed. Override exists (`--i-know-pilot-is-live`) for legitimate disaster recovery but requires explicit operator acknowledgement.

**First Windsurf+Sonnet PR** per the model split commitment in `PROMPT_AUTHORING_NOTES.md`. Spec is comprehensive enough that Sonnet should execute cleanly.

**Deploy class:** TS-only — no callable changes, no Firestore rules, no client OTA. Just script edits + new helper + tests + one Firestore Console flag-flip on the day pilot goes live (documented but NOT done as part of this PR).

## Plan

### §A — New shared helper module: `scripts/livePilotGuardHelpers.ts`

Two pure helpers + a discriminated-union Result (Rule 14 — server-side validators return Results, not throws; applies here even though it's a script because the pattern is the same).

```ts
/**
 * PR 39.2 — Live-pilot guard. Read by all three reset scripts at
 * startup to refuse deletion when the pilot is live (a real
 * customer has placed a real money order against this Firestore
 * project).
 *
 * Two layers:
 *   1. `parsePilotStatusFlag` — interpret raw Firestore doc data
 *      into a normalized boolean. Strict equality on
 *      `data.isLive === true`; any ambiguity (missing doc,
 *      missing field, truthy non-boolean) resolves to `false`
 *      (safe = pre-pilot). The flag's job is to say YES we're
 *      live; absence of YES means we're not.
 *   2. `evaluateLivePilotGuard` — decide whether to proceed
 *      given the parsed flag + operator's `--i-know-pilot-is-live`
 *      override. Discriminated-union Result; caller maps the
 *      `not-ok` branch to a loud banner + process.exit(1).
 *
 * Read-failure posture (in the glue, NOT this pure helper):
 * fail-CLOSED — treat read errors as if isLive=true. Cost of
 * refusing during a transient outage is "wait + retry";
 * cost of fail-OPEN is potential data loss. The glue lives in
 * the main scripts and is dry-run-smoke-tested per
 * test-discipline.md.
 *
 * Nothing in this file may import firebase-admin — same posture
 * as the other helpers split, so these can be unit-tested
 * without booting the SDK.
 */

export type ParsePilotStatusInput = unknown;

/**
 * Parse a Firestore doc snapshot's `.data()` (or null if doc
 * doesn't exist) into a normalized isLive boolean.
 */
export function parsePilotStatusFlag(rawDocData: ParsePilotStatusInput): boolean {
  if (rawDocData == null || typeof rawDocData !== 'object') return false;
  const data = rawDocData as Record<string, unknown>;
  return data.isLive === true;
}

export type LivePilotVerdict =
  | { ok: true; reason: 'pilot_not_live' | 'override_acknowledged' }
  | { ok: false; reason: 'pilot_is_live_no_override' };

/**
 * Pure decision: given the parsed flag + operator's explicit
 * override flag, should we proceed with the wipe?
 */
export function evaluateLivePilotGuard(args: {
  isLive: boolean;
  overrideAcknowledged: boolean;
}): LivePilotVerdict {
  if (!args.isLive) return { ok: true, reason: 'pilot_not_live' };
  if (args.overrideAcknowledged) {
    return { ok: true, reason: 'override_acknowledged' };
  }
  return { ok: false, reason: 'pilot_is_live_no_override' };
}

/**
 * Build the loud refuse banner shown when the guard refuses.
 * Pure function returning a string so it's testable without
 * touching console.log.
 */
export function buildLivePilotRefuseBanner(): string {
  const W = 60;
  const line = '═'.repeat(W);
  const blank = '║' + ' '.repeat(W - 2) + '║';
  const center = (s: string) =>
    '║ ' + s.padEnd(W - 4).slice(0, W - 4) + ' ║';
  return [
    '╔' + line.replace(/═/g, '═') + '╗',
    center('✋ PILOT IS LIVE — RESET REFUSED'),
    '╠' + line + '╣',
    blank,
    center('appConfig/pilotStatus.isLive = true'),
    blank,
    center('This wipe would destroy live customer orders,'),
    center('shop data, or partner ratings. The script is'),
    center('refusing to proceed.'),
    blank,
    center('If you are CERTAIN this is intentional disaster'),
    center('recovery AND you have coordinated with at least'),
    center('one other human, re-run with:'),
    blank,
    center('    --i-know-pilot-is-live'),
    blank,
    center('Otherwise, do nothing. The flag at'),
    center('appConfig/pilotStatus is the canonical signal.'),
    blank,
    '╚' + line + '╝',
  ].join('\n');
}
```

### §B — Pure-helper tests: `tests/scripts/livePilotGuardHelpers.test.ts`

Cover **11 cases** total:

**parsePilotStatusFlag (7 cases):**
1. `null` → `false` (doc doesn't exist)
2. `undefined` → `false`
3. `{}` → `false` (doc exists, no isLive field)
4. `{ isLive: true }` → `true` (the only true case)
5. `{ isLive: false }` → `false`
6. `{ isLive: 'true' }` → `false` (strict equality; string truthy ≠ boolean true)
7. `{ isLive: 1 }` → `false` (strict equality; numeric truthy ≠ boolean true)

**evaluateLivePilotGuard (4 cases):**
8. `isLive: false, overrideAcknowledged: false` → `{ ok: true, reason: 'pilot_not_live' }`
9. `isLive: false, overrideAcknowledged: true` → `{ ok: true, reason: 'pilot_not_live' }` (override irrelevant when not live)
10. `isLive: true, overrideAcknowledged: false` → `{ ok: false, reason: 'pilot_is_live_no_override' }`
11. `isLive: true, overrideAcknowledged: true` → `{ ok: true, reason: 'override_acknowledged' }`

No tests for `buildLivePilotRefuseBanner` — it's a pure constant-output formatter; manual inspection is enough.

### §D — Integrate the guard in each script's `main()`

After the existing flag parsing + admin UID resolution + Firestore init, BEFORE any deletion:

```ts
// Read pilot status with fail-CLOSED posture.
async function readPilotStatusIsLive(db: FirebaseFirestore.Firestore): Promise<boolean> {
  try {
    const snap = await db.doc('appConfig/pilotStatus').get();
    if (!snap.exists) return false; // pre-pilot — missing doc means safe
    return parsePilotStatusFlag(snap.data());
  } catch (err) {
    console.error(
      `${C.red}[livePilotGuard] flag read failed; FAILING CLOSED${C.reset}`,
      err,
    );
    return true; // can't confirm safety → treat as live
  }
}

// ... in main(), after initializeApp + db setup:
const isLive = await readPilotStatusIsLive(db);
const verdict = evaluateLivePilotGuard({
  isLive,
  overrideAcknowledged: flags.iKnowPilotIsLive,
});

if (!verdict.ok) {
  console.error('\n' + buildLivePilotRefuseBanner() + '\n');
  process.exit(1);
}

if (verdict.reason === 'override_acknowledged') {
  // Loud warning — operator USED the override. Make this maximally
  // visible in their terminal scrollback so a future audit catches it.
  console.log(`\n${C.red}${C.bold}⚠️  --i-know-pilot-is-live USED${C.reset}`);
  console.log(`${C.yellow}    Pilot IS live. Operator override acknowledged.`);
  console.log(`    This action will be in the audit log.${C.reset}\n`);
}

console.log(
  `${C.dim}  pilot guard   isLive=${isLive} verdict=${verdict.reason}${C.reset}`,
);
```

Apply same block to all three scripts. The `C` (color constants) object already exists in each.

**Dry-run behavior:** the guard runs in dry-run mode too. Pre-PR, an operator running dry-run on a live-pilot project would see the planned deletion list without warning. Post-PR, dry-run also reports the guard state — operator sees the refuse banner during dry-run before they ever pass `--execute`.

- **Notification to admin team when the override is used.** Audit log is sufficient for pilot scale.
- **Per-script override flag names** (`--i-know-reset-pilot-data-is-live`, etc.) — single shared flag name is fine; pure consistency wins over per-script naming.
