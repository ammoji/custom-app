# PR 36.1 — Pilot UX polish bundle (Windsurf prompt)

## Why this PR exists

During real-device testing of PR 31 + PR 32 + PR 34 + PR 38.1,
Sudhir surfaced 5 UX observations. Three are pilot-blocking
polish; two are bigger deferrals (separate ratings → PR 42.1;
smart substitution → PR 53.1). PR 36.1 ships the two
genuinely small polish items that materially improve pilot
UX with zero risk and zero recurring cost.

**Originally PR 36.1 was a 3-part bundle.** Part 1 was a fix
for the shop-side status-change delay (4–5 s on the first
tap, observed during PR 38.1 smoke testing). The diagnostic
in this session confirmed it as Cloud Functions Gen 2 cold
start (first tap ~4 s when function is cold, ~1 s when
warm — verified by tap-then-tap-again pattern returning 1 s
each on a fully warm function). The fix would be a single-line
`minInstances: 1` config addition to `updateOrderStatus` at
~₹400/mo per warm instance. Sudhir chose to defer it per
cost-conservative pilot stance — accept the 2–3× daily
cold-start hit during pilot, revisit post-pilot if it
surfaces as real friction. PR 36.1 therefore ships only the
two zero-cost polish wins.

**What ships:**

- **Part 1: Countdown timer alongside absolute pickup time**
  on customer-side `OrderDetailScreen`. "Ready in 22 minutes
  (by 7:30 PM)" — display both, decrement live every minute.
  Eliminates the mental-math friction every customer hits
  when checking on their order ("when's 7:30 vs now?").
- **Part 2: "Favorites only" filter pill** on `ShopListScreen`
  (and `SearchScreen` if applicable). PR 19 added favorites
  (Home tile + dedicated `FavoritesScreen`); what's missing
  is the inline filter pill to quickly toggle the list to
  favorites only without leaving the browse view.

~3 hrs Windsurf work. OTA-eligible. No new SDKs, no native
changes, no Cloud Function deploys, no rules changes.

## Critical lessons from PRs 25–38.1 (do not repeat)

1. **OTA-eligible.** No plugin, permission, or native dep
   changes. Verify in the diff before commit: `git diff
   main -- app.json package.json` should be empty.
2. **Never strip imports between edits.** Files touched:
   `OrderDetailScreen.tsx` (one new component + one new
   import), new `src/utils/formatRelativeTime.ts`,
   `ShopListScreen.tsx` (one new pill + useProfileStore
   import), maybe `SearchScreen.tsx`, new test file. All
   imports stable across edits.
3. **All `useState` calls in screens sit ABOVE conditional
   early returns.** `ShopListScreen` will get a new
   `useState<boolean>` for the filter pill state; declare it
   at the top with the existing hooks.
4. **`setInterval` cleanup in `useEffect`.** Part 1's countdown
   recomputes every 60 s. The `useEffect` MUST return a
   cleanup function clearing the interval, or the component
   leaks timers on unmount. Standard React pattern; mention
   it because timer leaks have historically been a class of
   subtle bugs.
5. **Verify field names against source first.** PR 36's
   `userId`/`address` vs `customerUid`/`deliveryAddress`
   correction is fresh. Before writing the countdown logic
   that references `readyByEstimate` or any other field,
   open the actual `Order` type and confirm.
6. **Strategic Principle 8 — instrumentation.** Both parts
   are UX additions a customer interacts with directly. Wire
   a small Analytics event for each:
   - `customer_pickup_countdown_viewed` — fires on
     OrderDetailScreen mount when an order has an ETA in the
     future. Useful signal for "are customers actually using
     the order tracking surface."
   - `customer_favorites_filter_toggled` — fires when the
     filter pill is tapped. Tells us whether favorites
     actually drive browse behavior.
   Both events auto-mirror to `featureUsageLog/` via PR 38.1
   routing.
7. **No new `DO NOT REMOVE` markers expected.**

**Pure helper:** create `src/utils/formatRelativeTime.ts`:

```ts
/**
 * PR 36.1 — Format a future timestamp as a human-friendly
 * relative duration ("in 22 minutes", "in 1 hour 5 minutes",
 * "any moment now", "X minutes ago" for past).
 *
 * Pure — no side effects, no Date.now() inside. Caller passes
 * `nowMs` so the function is deterministic and unit-testable.
 *
 * Locale: English for v1. The hi-IN version comes when
 * customer-side i18n lands (out of scope per the deferred
 * customer-i18n follow-up logged in PR 34).
 */

export type RelativeTimeResult = {
  primary: string; // "Ready in 22 minutes" / "Ready in 1 hour 5 minutes"
  isPast: boolean; // true if target is now or earlier
  totalMinutes: number; // signed: positive = future, negative = past
};

export function formatRelativeTime(
  targetMs: number,
  nowMs: number,
  options?: { label?: string; pastLabel?: string },
): RelativeTimeResult {
  const label = options?.label ?? 'Ready';
  const pastLabel = options?.pastLabel ?? 'Ready';
  const deltaMs = targetMs - nowMs;
  const totalMinutes = Math.round(deltaMs / 60_000);

  if (totalMinutes <= 0) {
    if (totalMinutes >= -2) {
      return {
        primary: `${pastLabel} any moment now`,
        isPast: true,
        totalMinutes,
      };
    }
    const ago = Math.abs(totalMinutes);
    if (ago < 60) {
      return {
        primary: `${pastLabel} ${ago} minute${ago === 1 ? '' : 's'} ago`,
        isPast: true,
        totalMinutes,
      };
    }
    const hours = Math.floor(ago / 60);
    const mins = ago % 60;
    const hoursPart = `${hours} hour${hours === 1 ? '' : 's'}`;
    const minsPart = mins > 0 ? ` ${mins} minute${mins === 1 ? '' : 's'}` : '';
    return {
      primary: `${pastLabel} ${hoursPart}${minsPart} ago`,
      isPast: true,
      totalMinutes,
    };
  }

  // Future.
  if (totalMinutes < 1) {
    return {
      primary: `${label} in less than a minute`,
      isPast: false,
      totalMinutes,
    };
  }
  if (totalMinutes < 60) {
    return {
      primary: `${label} in ${totalMinutes} minute${totalMinutes === 1 ? '' : 's'}`,
      isPast: false,
      totalMinutes,
    };
  }
  const hours = Math.floor(totalMinutes / 60);
  const mins = totalMinutes % 60;
  const hoursPart = `${hours} hour${hours === 1 ? '' : 's'}`;
  const minsPart = mins > 0 ? ` ${mins} minute${mins === 1 ? '' : 's'}` : '';
  return {
    primary: `${label} in ${hoursPart}${minsPart}`,
    isPast: false,
    totalMinutes,
  };
}
```

**Component wiring in `OrderDetailScreen.tsx`:**

```tsx
import { formatRelativeTime } from '../utils/formatRelativeTime';

// Inside the component, hoisted ABOVE any conditional early return:
const [nowMs, setNowMs] = useState(Date.now());

useEffect(() => {
  // Recompute every 60 s so the countdown ticks. Cleanup
  // clears the interval on unmount; without this, the
  // component leaks the timer.
  const id = setInterval(() => setNowMs(Date.now()), 60_000);
  return () => clearInterval(id);
}, []);

// Inside the JSX, replace the existing "Ready by HH:MM" line
// with the two-line layout. `readyByEstimate` is the existing
// field (verify against the Order type before referencing).
{order?.readyByEstimate && (() => {
  const r = formatRelativeTime(order.readyByEstimate, nowMs);
  return (
    <View style={styles.pickupRow}>
      <Text style={styles.pickupPrimary}>{r.primary}</Text>
      <Text style={styles.pickupSecondary}>
        by {formatTime(order.readyByEstimate)}
      </Text>
    </View>
  );
})()}
```

**Analytics:** at mount when `order.readyByEstimate` exists and
is in the future:

```ts
useEffect(() => {
  if (!order?.readyByEstimate || order.readyByEstimate <= Date.now()) return;
  Analytics.customer_pickup_countdown_viewed({
    order_id: orderId,
    minutes_until_ready: Math.round((order.readyByEstimate - Date.now()) / 60_000),
  });
}, [order?.id, order?.readyByEstimate, orderId]);
```

**Edge cases the formatter handles:**

- ETA already passed by <2 minutes → "Ready any moment now"
- ETA passed by 2–59 minutes → "Ready 15 minutes ago"
- ETA passed by 1+ hours → "Ready 1 hour 5 minutes ago"
- ETA in <1 minute → "Ready in less than a minute"
- ETA in 1–59 minutes → "Ready in 22 minutes"
- ETA in 1+ hours → "Ready in 1 hour 5 minutes"

**Edge case: no ETA set.** If `order.readyByEstimate` is null
or undefined (the shopkeeper hasn't entered one), don't render
the pickup row at all. Don't display "Ready in NaN minutes."

const NOW = 1_700_000_000_000;

## Why this PR matters

Both items are small individually; together they're the kind
of pre-pilot polish that disproportionately affects customer
experience.

**Countdown timer:** the "Ready by 7:30 PM" → "Ready in 22
minutes" change eliminates a mental-math step every time a
customer checks on their order. Most users check their order
2–5 times before pickup. That's 2–5 small frustrations per
order × ~3 orders/customer/month × 50 customers in pilot =
~500 micro-frustrations/month avoided. The friction is small
per instance but compounds across the cohort.

**Favorites filter:** the favorites feature has existed since
PR 19, but a customer who wants to "just order from my regular
shop" today has to either remember the shop name (and use
search) or navigate to the dedicated FavoritesScreen. The
inline filter pill makes "regular shop" a one-tap default
from anywhere in the browse flow. Strategic Principle 4 is
about merchant daily-use hooks; this is the customer-side
equivalent — making the platform feel like *their* personal
shopping shortlist.

After PR 36.1 ships, the **last pilot-blocking development
work is done.** Remaining items are non-code: final app-name
commit (MeraYara or alternative), real branding artwork (icon,
splash), `[CITY TBD before launch]` replacement in ToS §13,
and manual onboarding of the first 5–10 pilot shops. Then
pilot starts.
